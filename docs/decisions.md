This is a research record. For current setup and commands, start with
[Evaluate your data](EVALUATE.md). Costs and timings below belong to the cited runs.
- **D69 A round executes SQL the model wrote, and it had no row cap.** The second Acme round asked all 78 questions across four arms, then sat for twenty minutes with no BigQuery job running, 48 open sockets and memory climbing: **6,045 MB, then 6,516 MB forty-five seconds later, about 10 MB a second.** It was fetching one result set into Python. All 39 clean golds returned under 10,000 rows at gate time, so this was a PREDICTION — SQL a language model wrote, which is untrusted output by definition, and `round` had no `--row-cap` flag at all. On a smaller machine the operating system would have killed it. This is D61 in the stage where it matters most, and the same one-of-two-copies fault as D65: `mine` and `gate` both took the flag and `round` did not. The scoring layer was already correct and had simply never been reached — `harness._evaluate_one` returns `ROW_CAP_HIT` and EXCLUDES a capped row rather than comparing a full result to a cut one, because a mismatch between them reads as a real failure and calling it wrong invents one. So the fix is a default and not a flag: `DEFAULT_ROW_CAP = 10_000` now applies to every command that executes SQL, eight of them, with `--row-cap 0` for anybody who means no cap. 10,000 is generous — a business question's answer is tens or hundreds of rows — and it is not there for the golds, it is there for the predictions. A structural test fails if any command that runs SQL defaults to None again. Rejected: capping only `round`, which would have left `score`, `attribute`, `climb` and `triage` exposed to the same untrusted SQL.

- **D70 The agent call had no deadline, and a bigger arm makes the agent much slower.** The heartbeat from D65 paid for itself on its first real run: `round/0d 5m00s [###?------------] 4/21 stuck 3m27s 0 call retries` — which item, how long, and no retries, three facts that this morning cost `lsof`, `ps -M` and counting BigQuery jobs from another terminal. Two things came out of it. **First, a correction to what I assumed**: the item was slow, not hung, and cleared after 3m27s. So the missing deadline is a latent risk rather than today's cause, and I should say so rather than let the fix look like a diagnosis. **Second, the measurement worth keeping**: same questions, same model, K=1, and the only change was the arm. A 27-table arm answered in about **28 seconds** a question. An 85-table arm took **60 to 210 seconds**, one call 3m27s, with **zero retries** — so that is the service thinking about a bigger prompt, not a network fault. Roughly a sevenfold slowdown for three times the tables, which is a real cost of the table-coverage fix (D67) and should be priced before anybody puts hundreds of tables in an arm. The fix is still right on its own terms: `client.chat` took no `timeout`, so one stream that never ends blocks every question behind it, and on a 78-question round that is 77 waiting on one. `CHAT_TIMEOUT_SECONDS = 300`, above the slowest call actually measured so it cannot throw away an answer the service would have given, and `None` for anybody who wants the old behaviour. It composes with what already existed: `DeadlineExceeded` is in `TRANSIENT`, so an expired call is retried four times with backoff and **counted**, and the heartbeat prints the count — so a slow call and a retried call are finally different words on the screen. Rejected: 60 seconds, which would have failed a third of this run's questions and read as the agent being wrong.

- **D71 A round threw itself away over two questions of eighteen, and the row cap was why.** The third Acme round asked all 78 questions across four arms in 45 minutes and then died on its last statement: `ValueError: the two arms did not score the same questions, so they cannot be paired. scored only with context: ['m027_9d8baba1#rep0', 'm360_f44f0638#rep0']`. The cause was D69's own fix one hour old: a control prediction hit the new 10,000-row cap, became `ROW_CAP_HIT` and was excluded, while the treatment's answer to the same question was fine. Excluding one arm and not the other breaks the pair. The refusal itself is right — a mispaired number gets quoted later without the caveat — but throwing away 45 minutes over 2 of 18 questions is the wrong remedy. **Two callers want opposite things, and the failing tests are what showed it.** Within ONE round, two arms answer the same golds in one process, so a difference in what they scored can only be a per-arm exclusion; pair what both scored and say how many were dropped. ACROSS runs — `climb` comparing rounds, `bundle` comparing saved reports — a differing set means the GOLD SET changed, and then the two numbers are not measuring the same thing at all, so those callers keep refusing. Hence `pair_common=False` by default and the round opting in, rather than changing the contract for everybody. Three details that make it honest rather than convenient. The rates are **rebuilt** over the common set through `_report_from_results`, because `execution` is a stored field and filtering results alone would leave an accuracy computed over questions no longer in the comparison — two numbers pretending to be one. Above `UNPAIRED_LIMIT = 0.20` it still refuses, because a row cap excluding one arm is ordinary and rare while an arm that stopped early is neither. And the count reaches the line a reader actually looks at: `held out: 16 of 18 questions (2 scored by only one arm)`. That last part needed a second fix — the first version put it in the ablation summary, and the round prints its own verdict block, which showed "16" on one line and "18" on the next. A helper already existed for exactly this, and it had survived because its condition also required a stored-example lookup. **The checkpoint from D68 made the whole repair cost two minutes**: `resuming: 78 answers already on disk` / `asked 0 from disk 21`, zero API calls, so a 45-minute run was re-scored rather than re-asked. Rejected: raising the row cap until nothing is excluded, which trades a visible exclusion for an invisible 6 GB.

- **D72 `split` wrote two files that `round` ignored, and the documented workflow therefore leaked reserved answers into the context.** D62 named this as a seam worth fixing; it is worse than that. `contextlift split --holdout-fraction 0.5` wrote 19 working and 20 reserved ids to `curate_ids.txt` and `holdout_ids.txt`. `round` never read them: it called `split_golds` on the same golds and got **21 working and 18 reserved**, and the two working halves overlapped on **10 ids of 19**. So nine golds a person had every reason to treat as working were reserved inside the round. Building a worked-example bank from "the working half" therefore handed the agent nine reserved answers, and the round refused with `leak: 9 of 18 held-out questions appear in what the agent is handed` and `template twin: 9 items are the same query shape as a scored question`. The gates did their job and the workflow was still broken: **anybody following the documented order would hit this, and a leak that manufactures a FALSE POSITIVE is the worst failure this tool can have** — it reports a lift that was substitution. Fixed by making the files authoritative: `run` takes an explicit `split`, and the CLI looks for the two files **beside `--golds`** and says which it used, because a step whose output nothing reads is a step people stop running, and silently using a file somebody forgot about is as bad as silently ignoring one. `--curate-ids` and `--holdout-ids` override, and go together — one half alone cannot say where the other questions went. Three refusals rather than a best effort: an id the gold set does not have means the split came from a different gold set; a gold in neither half means the split is stale; a gold in both halves means a question is being practised on and reserved at once. Rejected: passing `--holdout-share` and `--seed` to make both sides agree, which is what I did first. It makes the round's split deterministic without making it the same split, so the two numbers still disagree and nothing tells you.
